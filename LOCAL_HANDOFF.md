## 3. Install and run locally

The commands below are **handoff instructions**, not actions performed against the managed servers during this task. Start from an exported/cloned repository with its lockfiles and patches intact.

### Install (separately in each project)

```sh
cd backend
bun install --frozen-lockfile
cd ../mobile
bun install --frozen-lockfile
```

No dependency upgrades are required for this documentation handoff. If install fails on unavailable VibeCode packages or patches, preserve the failure and investigate; do not silently replace native dependencies.

### Environment setup

```sh
# From repository root, after checking that you will not overwrite existing local files:
cp backend/.env.example backend/.env.local
cp mobile/.env.example mobile/.env.local
```

Replace the example backend host with an address reachable by the emulator/phone. `EXPO_PUBLIC_BACKEND_URL` is the **mobile build-time** URL; `BACKEND_URL` is backend/shell configuration, not a substitute in mobile code. Never expose storage credentials, passphrases, or media keys through `EXPO_PUBLIC_*` variables.

**Existing backend dev-script precedence issue:** `bun run dev` currently specifies `.env.local` **before** `.env`. A nonsecret isolated Bun 1.2.19 probe confirmed the later `.env` wins duplicate names. Thus copying the example alone does not reliably override tracked `.env` values with that script. Without changing repository code, use shell-exported configuration (highest precedence), or run the equivalent local hot command with the files ordered explicitly:

```sh
cd backend
bun --env-file=.env --env-file=.env.local run --hot src/index.ts
```

The existing script is still `bun run dev`; the ordering above is an operator workaround, not a script change. Review the effective configuration before provisioning or running a production server. Expo loads mobile local dotenv files itself; changing `EXPO_PUBLIC_*` requires restarting bundling and rebuilding any distributed binary.

### Backend database and development

```sh
cd backend
bun run prisma:generate
# New local development database only:
bunx prisma db push
# Then start using your chosen environment handling:
bun run dev
```

Use the ordering workaround above when `.env.local` overrides duplicate tracked names. Prisma generation/schema setup is **not** performed by the direct `dev`/`start` package scripts. Development startup prepares development profiles/catalog when development bypass is enabled.

- Existing production/valuable databases: back up first, then use **`bun run migrate:deploy`**; do not use destructive `db push` or reset.
- Default dev SQLite path is `backend/prisma/dev.db` (`file:./dev.db` resolves beside the schema).
- Private-profile credentials: supply all six provisioning variables, explicitly disable development bypass, then run **`bun run provision`**. Provisioning writes household/profiles and can revoke sessions when credentials change; it was **not run against live data** by this task.
- Other existing commands: `bun run start`, `bun run dev:ensure-auth`, `bun run notifications:sweep`, `bun run studio` (Cloud Studio port 3001). `notifications:sweep` is finite; schedule it externally for time-driven deliveries/receipts/retries.
- `backend/scripts/start` is the VibeCode/runit wrapper, not the recommended minimal local launch: it installs, generates, synchronizes, and integrates platform services. In development its setup can use `db push --accept-data-loss`.

### Mobile development

```sh
cd mobile
bun run start       # Expo / Metro, default port 8081
bun run android     # expo start --android; launches a runtime, does NOT compile it
bun run ios         # Expo launch request; native iOS development needs macOS/Xcode
bun run web         # DARK_MODE=class expo start --web
```

Backend default port is 3000. For API checks export the local backend address into the shell's `BACKEND_URL`, then use:

```sh
curl "$BACKEND_URL/health"
```

Do not point a phone at its own localhost. A physical phone normally needs the computer's reachable LAN address or a trusted HTTPS tunnel. Native Android HTTP cleartext policy, LAN reachability, and browser CORS must be verified for the chosen setup. Current CORS covers localhost and platform preview origins; an arbitrary LAN web origin is not guaranteed to be allowed.

## 5. Backend, database, authentication, and storage

### API and database

Active backend provider is **Bun + Hono + Prisma + SQLite**, not Supabase/Firebase/Postgres. SQLite is intended for a single writer; `src/prisma.ts` enables foreign keys, WAL, busy timeout, and NORMAL synchronous mode.

Mounted paths (`backend/src/app.ts`): `/health`, `/api/bootstrap`, `/api/auth`, `/api/dev/auth`, `/api/spaces`, `/api/categories`, `/api/ideas`, `/api/lets-date`, `/api/destinations`, `/api/trips`, `/api/schedules`, `/api/memories`, `/api/media`, `/api/devices`. There is no mounted `/api/calendar` or `/api/settings` despite old architecture notes. Domain responses use `{ data: ... }`; the mobile API client unwraps the inner value and sends bearer headers. Health is a separate response.

Platform production startup uses `ENVIRONMENT=production`, `NODE_ENV=production`, and a default DB at `/data/production.db` through `scripts/env.sh`; `DATA_DIR` can change that path. **Direct `bun run start` does not apply those wrapper overrides**; configure its environment/database explicitly. Committed migrations are under `backend/prisma/migrations/` (11 at this snapshot).

### Authentication provider

**Custom fixed-profile authentication**, implemented in `backend/src/auth.ts`; no active Better Auth/OAuth/Firebase/Supabase provider. Exactly two configured private profiles in a household; handles/passphrases, Argon2id hashes, opaque bearer sessions stored as SHA-256 token hashes, rolling expiry/revocation, credential-version invalidation, and persisted login throttling. No public signup or public password-reset flow; recovery/provisioning is manual.

Mobile auth lives in `src/lib/auth/`: native session token in Expo SecureStore; web token in localStorage. Unauthorized restoration clears private caches/session state. Development profile sessions are strictly development-only. No `BETTER_AUTH_SECRET` or separate session-signing secret is read/required by current code; generic Better Auth project instructions are not evidence of that integration.

### File/image/media storage

- Default **private encrypted filesystem** provider: `backend/prisma/private-media` in development, `/data/private-media` in production unless overridden.
- Optional private **S3-compatible/R2** provider via `Bun.S3Client`, selected only with the full S3 configuration. R2 is an adapter option, not evidence of a configured cloud account.
- AES-256-GCM per-object encryption with wrapped data keys; DB contains metadata, not file bytes. Files include Idea images, Trip heroes, and Memory photo/video/voice-note contributions.
- Filesystem mode generates/persists `.master-key-v<version>` if no explicit key is set; restrictive directory/file permissions are applied. S3 mode requires an explicit 32-byte base64 master key.
- Authenticated no-store download/upload routes. Whole-object decryption; HTTP Range requests return **416**. Native playback uses downloaded temporary files; web uses Blob object URLs.
- Mobile native picker/media receipts and drafts use document-directory journals with AsyncStorage replicas, retained media, and temporary authenticated caches. Web uses AsyncStorage/localStorage. Planning-context Zustand selection is nonpersisted. Installed MMKV/SQLite packages are not active app persistence.

### Data transfer and backup — separate from source handoff

Git excludes local DBs/media. Before retiring VibeCode, securely export a **consistent SQLite backup**, encrypted media object directory/bucket, generated or supplied media master key and key-version information, and required profile/storage/push credentials. Do not copy a live SQLite DB alone while ignoring its WAL; use SQLite-aware backup or an offline copy. Preserve IDs and storage object references. A source-only clone does **not** contain current user data, sessions, drafts, or encryption keys. Device SecureStore/document journals remain device-local; a different app identity/install may not retain them.

No data export, secret retrieval/rotation, credential provisioning, or backup migration was performed here. Losing the media key makes the encrypted objects unrecoverable.
